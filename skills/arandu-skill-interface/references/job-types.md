# Job types

| Job | Signals | Preserve | Change | Steps |
|---|---|---|---|---|
| **New world** | no product UI yet, or skeleton defaults only | product truth the user gives | everything visual and textual | 1–8 |
| **Extend** | a new page or feature inside an established product | the product's world: tokens, type, shell, glossary | only the new surface | 3, 4, (5), (6), 7 |
| **Refine** | "make it premium", "polish", "harmonise" on an existing product | identity, behaviour, routes, contracts of components, factual copy | finish, states, hierarchy, consistency, text quality | 2 (document what exists), 3, 4, 5, 6, 7 |
| **Redesign** | "new look", "redesign", "rebrand" | product truth, content facts, functions, routes, data, accessibility | the visual world (DESIGN.md replaced), copy where it is weak | 1–8 |

## Refinement preserves; redesign replaces

- A refine job never smuggles in a new identity: if the concept itself is wrong, say so and ask for a redesign.
- A redesign never "splits the difference" by polishing the discarded look.
- In both, never change: authentication, authorisation, tenancy, data access, integrations, routes that are linked from outside, public URLs (without redirects), the CSP.

## Single-surface requests

A request about one surface inside an established product is an **extend** or a scoped **refine**: no identity exercise, no preset selection, no new DESIGN.md — inherit and finish.
